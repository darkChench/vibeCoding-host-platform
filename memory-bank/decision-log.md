# 决策与修改记录

本项目每一次决策和修改都在这里留痕：做了什么、为什么、放弃了什么、改了哪些文件、怎么验证的。
供后续开发和 AI Agent 查"某处为什么是这样"。规则见 [AGENTS.md](../AGENTS.md) 第 9 节。

## 使用约定

- **只追加，不改写**：新记录加在文末"记录"一节的末尾，按时间顺序排列，最新的在最后。发现旧记录有误，追加一条更正，不回头修改。
- **一个主题一条记录**：能独立理解的一个变化记一条；同一次改动里的零碎修改（如错别字）并入同批记录，不单独记。
- **记什么**：功能与行为变化、bug 修复、配置与打包方式变化、文档与规则变化。既记用户拍板的决定，也记 Agent 自行做出的判断（方案取舍、默认值、范围边界）。
- **标明谁定的**：每条决策以【用户决定】或【Agent 判断】开头，方便事后审查 Agent 的取舍。
- **放弃的方案只写真考虑过的**：不为凑格式编造选项。
- **不记敏感信息**：密钥、Token 等不写入。
- **与提交的关系**：记录先于提交写好，随同改动一起提交；提交后把"状态"里的"未提交"换成 commit 短哈希。
- **文件过长时**：超过约 2000 行，把最早的记录按年归档到 `memory-bank/decision-log-archive-<年>.md`。

领域术语以仓库根目录 [CONTEXT.md](../CONTEXT.md) 为准。

## 记录模板

每条记录包含以下几项，顺序固定：

- **标题**：`### YYYY-MM-DD 标题`，用一句话说明变了什么
- **背景**：为什么会有这次变化（问题、来源）
- **决策**：逐条列出，每条以【用户决定】或【Agent 判断】开头，并写明理由
- **放弃的方案**：考虑过但没有采用的选项，以及不采用的原因
- **修改**：逐个列出改动的文件和改了什么
- **验证**：怎么验证的，结果如何
- **状态**：未提交，或已提交并附 commit 短哈希

### 2026-11-25 串口原始日志：报文行按方向着色，去掉行首 TX/RX 标签

**背景**：串口页"串口原始日志"里，原先只有行首的 `TX`/`RX` 标签有颜色（TX 蓝、RX 绿），报文正文统一是深色，
长时间盯日志时不容易一眼分清收发方向。正文着色是在提出"记录所有决策"之前做的，
因为和去标签是同一处未提交的改动，合并成一条记录。

**决策**：

- 【用户决定】RX 报文显示为绿色，TX 报文显示为蓝色。
- 【用户决定】着色之后，行首的 `TX`/`RX` 标签去掉。
- 【Agent 判断】颜色直接沿用标签原有的两个色值（RX `#11875d`、TX `#0b6fb3`），不引入新颜色；终端是白底，这两个深色可读。
- 【Agent 判断】正文着色只对报文行（标签为 `TX`/`RX` 的行）生效。诊断行（TIMEOUT/CRC/WARN）走同一个渲染函数，
  并且同样带 tx/rx 方向，按方向上色会把"超时"显示成绿色。
- 【Agent 判断】只去掉 `TX`/`RX` 两个标签。TIMEOUT、WARN、INFO 等标签不在要求范围内，保持原样。
- 【Agent 判断】只改终端显示。内存里的日志数据和保存到 `history/` 的 txt 文件仍然带 `TX`/`RX` 标签，
  因为纯文本没有颜色，去掉就分不清收发。

**放弃的方案**：

- 所有行的正文都按方向上色，不区分报文行和诊断行：超时信息会变成绿色，与"绿色代表正常"的直觉相反。
- 把"通信统计"页签里的 `TX`/`RX` 标签一并去掉：不属于"串口原始日志"，没有动。

**修改**：

- `vibe-hmi/src/pages/serial_page.py`：`_append_to_terminal` 中报文行正文改用方向色、不再渲染行首标签；
  文件头注释里与实际相反的配色说明（原写"暗底，TX 绿 / RX 蓝"）改为与实际一致。
- `vibe-hmi/tests/test_serial_page_terminal.py`：新增 4 个用例，覆盖 RX 着色、TX 着色、诊断行不着色且保留标签、INFO 行不着色且保留标签。

**验证**：

- 在 `vibe-hmi/` 下运行 `.venv\Scripts\python.exe -m pytest tests/`：53 个全部通过。新增用例先失败（正文仍是深色、标签仍在），修改后通过。
- 离屏渲染截图确认：TX 行整行蓝色、RX 行报文绿色，行首无标签；INFO 行正文深色、WARN 行红色，标签保留。

**状态**：已提交（8b904d3）

### 2026-11-25 建立决策与修改记录机制（本文件）

**背景**：在此之前的决策散落在对话记录、commit message 和 memory-bank 的规划文档里，文件中只有"做了什么"。
"为什么这样做、放弃了什么"没有落到文件，例如"历史采样记录不新增从机地址列""多设备同图对比本期不做"
"AI 助手查历史仍按全局当前设备"这几个决定只存在于对话里，事后查不到依据。
用户要求从现在起，所有决策和修改都记录到文件。

**决策**：

- 【用户决定】所有决策和修改都必须记录到文件。
- 【Agent 判断】用一份按时间顺序追加的单文件 `memory-bank/decision-log.md`，而不是每个决策一个文件。要求覆盖的是"所有"变化，其中大部分是很小的改动，单文件写入成本最低，查的时候也只有一个地方。
- 【Agent 判断】文件放在 `memory-bank/`。该目录的定位就是为 AI 提供持久、稳定的项目上下文，决策记录和规划文档是同一类东西；同时不新增根目录文件，保持根目录扁平。
- 【Agent 判断】每条决策标明是"用户决定"还是"Agent 判断"，方便事后审查 Agent 自己做的取舍。
- 【Agent 判断】`docs/adr/` 维持原有定位，只留给难以逆转、需要单独论证的架构决策，日常改动不写 ADR。
- 【Agent 判断】规则写进 `AGENTS.md`，而不是只存在于对话里，这样以后的会话也会执行。
- 【Agent 判断】记录从本条开始，不回填更早的历史，更早的工作以 git 历史里的 commit message 为准。依据是用户说的"从现在开始"；用户没有明确说不回填。

**放弃的方案**：

- 每个决策一个 ADR 文件（`docs/adr/`）：适合大型架构决策，日常小改动用它太重，也很难坚持"所有"都记。
- 按功能目录记录（`.scratch/<feature>/`）：那是 issue 和 spec 的位置，内容按功能分散，不便于按时间总览全部变化。

**修改**：

- 新增 `memory-bank/decision-log.md`（本文件）：使用约定、记录模板和记录正文。
- `AGENTS.md`：Golden Path 新增"记录本次决策与修改"一步（排在提交之前）；第 9 节新增"决策与修改记录（强制）"；
  第 10 节 Memory Bank 文件清单加入本文件；第 6 节的项目结构注释和关键入口文件同步；提交前清单增加一项。
- `README.md`："入口导航"加入"决策与修改记录"。
- `vibe-hmi/AGENTS.md`：新增"记录要求"一节；把"memory-bank 三份规划文档"的表述改为与本文件不冲突。

**验证**：`make test` 通过（Markdown lint、链接检查、结构检查等全部质量门禁）。

**状态**：已提交（7877924）

### 2026-11-26 串口日志：数据多时切页签、切时间戳、切 HEX 冻结十余秒

**背景**：用户反馈"串口原始日志数据很多时上位机很卡顿，清空就好了"。
实际设备每秒主动推送一条 152 字节的文本帧，应用连续运行几小时后存储的日志达到一两万行。
实测存储 15,800 行时：切回"串口原始日志"页签冻结 10.5 秒，勾选时间戳 8.8 秒，切换 HEX/ASCII 17.7 秒；
清空后同样的操作只要 0~2 毫秒。

**决策**：

- 【Agent 判断】根因不是"来一行日志的开销随数据量增长"。单独的串口页在短行/长行、屏幕外/屏幕上、
  到顶前后、上万次删旧行等各种条件下，每行开销都稳定在 1 毫秒左右；对用户正在运行的实例做只读探测，
  空闲时主线程消息响应最大延迟 5 毫秒。真正的原因是切页签、勾选时间戳、切换 HEX/ASCII 会触发终端整体重绘，
  原实现把存储的全部日志逐行 appendHtml 重画一遍，而终端最多只保留 5000 行，
  其余一万多行是"画完立刻被丢弃"的无用功。
- 【Agent 判断】整体重绘只渲染终端留得住的最后 5000 行。最终显示的内容和原来完全一样，纯粹去掉无用功。
- 【Agent 判断】多行写进同一个编辑块，并且不再拼 HTML，改用 QTextCursor 直接写带格式的文本。
  实测重画 5000 行：逐行 appendHtml 2099 毫秒，单个编辑块内逐行插 HTML 404 毫秒，
  整段 setHtml 305 毫秒，直接写带格式文本 38 毫秒。
- 【Agent 判断】"一行日志怎么显示"（哪几段文字、各是什么颜色）抽成 `_line_segments`，作为唯一定义；
  实时追加和整体重绘共用，避免两条路径显示不一致。因此实时追加也一并改走新写法。
- 【Agent 判断】HEX→ASCII 转换从逐字节循环改成整帧一次转换。剩下约 0.39 秒的重绘耗时里，这一步占 0.35 秒。
  转换规则不变，用"与旧实现在 500 个随机帧上结果一致"的测试锁定。
- 【Agent 判断】顺带修掉两个原本就有的显示错误，都在同一个函数里、各是一处条件：
  1. 诊断日志行（TIMEOUT/CRC/WARN）带 rx/tx 方向，在默认的 ASCII 模式下被当成 HEX 帧转换，
     整行显示成 `TIMEOUT  .........`。现在只有报文行才做 HEX 转换。
  2. 内容原来按 HTML 渲染，设备输出里的 `<b>ok</b>` 这类文字会被当成标签吃掉，连续空格被压成一个。
     改成直接写文本后原样显示。

**放弃的方案**：

- 只把重绘改成单个编辑块、仍逐行插 HTML（404 毫秒），或整段 setHtml（305 毫秒）：
  能消除十几秒的冻结，但留下 0.3~0.4 秒的停顿，而且继续依赖 HTML，上面两个显示错误修不掉。
- 行间用 `<br>` 拼成整段 HTML：QPlainTextEdit 会把全部内容并成一个文本块，行数上限失效，直接排除。
- 实时追加保持原来的 appendHtml、只改整体重绘：两条路径各维护一套颜色逻辑；
  而且 HTML 会压缩空格，重绘之后和实时追加的显示会有细微差别。
- 调低终端保留行数（比如 2000 行）：能进一步缩短重绘时间，但会减少用户能回看的日志量。
  这是产品层面的取舍，没有擅自改。

**修改**：

- `vibe-hmi/src/pages/serial_page.py`：新增 `_line_segments`、`_stats_segments`、`_char_format`、`_render_lines`、
  `_scroll_to_bottom`；`_append_to_terminal`、`_refresh_terminal` 改为调用它们；`_hex_to_ascii` 改为整帧转换，
  `\r\n` 直接产出块内换行符（不再经过 `<br>`）；新增常量 `TERMINAL_MAX_LINES`、`TEXT_COLOR`、`TIMESTAMP_COLOR`、
  `ASCII_LINE_BREAK`。
- `vibe-hmi/tests/test_serial_page_refresh.py`（新增）：整体重绘 = 清空 + 一次写入；只渲染最后 N 行；重绘后显示的是最新行。
- `vibe-hmi/tests/test_serial_page_terminal.py`：改为直接检查终端里实际渲染出的文字和颜色（原来检查的是 HTML 字符串）；
  新增 ASCII 原样显示、诊断行不被当成 HEX、HEX→ASCII 映射规则及与旧实现一致的用例。
- `vibe-hmi/tests/test_serial_page_threading.py`：探针从"截获 appendHtml"改为"监听终端文档被修改时所在的线程"，
  守护的不变量（终端文档只能在主线程修改）不变。
- 行为变化：ASCII 模式下设备输出里的 `<` `>` `&` 和连续空格原样显示；诊断日志在 ASCII 模式下可读；
  时间戳与内容之间、标签与内容之间保留两个空格（原来被 HTML 压成一个）。
- 过程中的失误：测量脚本追加超过 2.1 万行时触发了"满 10MB 自动保存"，在用户的 `history/` 目录里写出了
  两个合成日志文件。核实内容后已删除，用户的真实日志没有受影响。之后的测量脚本要先把 `HISTORY_DIR` 指到临时目录。

**验证**：

- 在 `vibe-hmi/` 下运行 `.venv/Scripts/python.exe -m pytest tests/`：69 个全部通过。
  新增用例先对修复前的源码跑过，确实失败。
- 新旧渲染并排截图（ASCII、HEX 两种模式）：版式和颜色一致；新实现的实时追加与整体重绘一致。
- 完整应用冒烟（真实 MainWindow + 轮询，30 秒加速）：无异常，无跨线程警告。
